一句话产品定义

讲给老板听的版本

把新员工的话术训练，从「老带新、靠悟性」变成「微信式仿真陪练 + 自动评分 + 风险预警」——每名新员工在入职两周内，用微信聊天的方式和 AI 扮演的客户把必修场景练到达标线，管理者当天就能看到谁需要辅导、弱在哪一维。

学员端不是又一个在线课程，而是一个可对话、可打分、可复盘的练习场：客户会压价、会投诉、会说「我在忙」，学员用文字、语音条或语音通话回应，系统按 5 个能力维度实时打分，练习结束即出报告。管理后台把这份报告变成可执行的运营动作（下发任务、看完成率、按红黄绿分层）；教练工作台则把它变成带教动作（看我的学员弱在哪、写一对一辅导记录、抽检对话统一话术）——三端共用同一份数据与同一个评分引擎。

为什么做这个系统

问题陈述

① 反馈慢。新员工第一次真接客户，反馈要等主管复盘，一次练习的反馈周期以天计；说错了当场没人纠正，错了就重复错。

② 无法量化。「这孩子挺机灵」是最常见的评价。谁的需求挖掘弱、谁的异议处理不会接情绪，全靠印象，无法比较、无法排序。

③ 无法复盘。实战过程没有留痕，培训后再想找「他当时是怎么回这一句的」无从查起，优秀话术也沉淀不下来。

④ 依赖老带新。带教主管时间有限，一次只能带一两个人；新员工越多，辅导质量越稀释，经验也随人走。

结论：缺的不是课件，而是练习场和反馈。新员工需要的是一次可以反复失败、且每次失败都有人（或系统）明确指出「哪一句、错在哪」的机会——这正是本系统要提供的。

06

评分机制

原型阶段：关键词命中（scoring-engine.js） → 目标阶段：大模型 Rubric

原型阶段 · 关键词命中代理

现状

学员端先跑通「练习 → 评分 → 报告」的完整链路，用最便宜的办法产生分数：一份关键词命中表 TRAIN.kw（5 维共 – 个词）充当打分代理。

评分逻辑不写在页面里，而是抽成纯函数模块 data/scoring-engine.js（window.SCORER）。学员端判分、教练端给弱项建议、管理端复核分数，全部调用同一个 scoreTurn()——一处修改，三端同步，杜绝"两端算法打架"。

初始每维 42 分 → 命中该维任一关键词：+13（该维上限 97）
当轮考察目标达成 且 命中目标对应维度：再 +6
语音通话中发言：命中维度补差到 +9（非叠加）

综合分 = 5 个维度得分的算术平均（helpers.avg，四舍五入），再与达标线比较得出是否达标。

接口（3 个消费方共用）：

SCORER.detectHits(text, kw, dimIds) → 命中维度 id 列表
SCORER.scoreTurn(text, ctx) → 该轮 5 维得分 + 命中明细
SCORER.scoreSession(session) → 整场综合分 / 达标判定
SCORER.compareWithHistory(result, history) → 与历史同场景成绩对比
SCORER.suggestionsFor(weakDims) → 弱项 → 带教建议

它解决了什么：零成本、零依赖（file:// 双击即用）、即时出分、完全可解释，让端到端体验先立起来。

目标阶段 · 大模型 Rubric 评分

目标

关键词只能判断「有没有出现」，判断不了「有没有用对」。目标方案把评分交给大模型：输入场景剧本、训练目标、学员每一轮发言（语音先经 ASR 转文本）与上下文，模型按 5 维 Rubric + 权重输出结构化评分。

综合分 = Σ(dimScore × weight) / 100
达标：综合分 ≥ task.passLine（任务下发时可覆盖场景默认线）

输出除了分数，还要有证据（引用学员原话）、目标达成逐条判定、置信度与改进建议——分数要能被主管复核，而不是一个黑盒数字。

替换成本被引擎隔离到最小：scoreTurn() 的入参出参形状保持不变，内部由"关键词匹配"换成"模型调用"即可，三端的调用代码一行不改。

关键约束：Rubric 版本化管理；低置信度样本转人工；每月用金标集校准，保证与人工评分的一致性。

指标定义

公式与 helpers 实现完全一致

完成率

–%
已完成学员数 / 应完成学员数 × 100%

口径：分母 = Task.assignees 去重人数；分子 = 该任务下已存在 Record 的学员数（同一人多次练习只计一次，取最新记录）。当前口径取自 helpers.taskProgress().rate。

达标率

–%
达标记录数 / 已完成记录数 × 100%

口径：达标 = Record.passed（即 score ≥ passLine）。单任务达标率只算该任务；整体达标率按全部 Record 统计——两者不可混用，看板须标注清楚。

平均分

–分
Σ Record.score / Record 条数（四舍五入）

口径：统一走 helpers.avg，与维度平均分、单任务平均分共用同一个取整规则，避免各处结果不一致。

风险分层

–人待关注
按 red → yellow → green 顺序命中即停

口径：以学员全部历史记录计算最近一次是否达标与历史均分，规则严格取自 TRAIN.riskRules，见下。

风险分层规则

文案一字不差取自 TRAIN.riskRules

判定顺序（helpers.riskOf）

1. 无任何练习记录 → yellow（需关注）
2. 最近一次未达标 且 历史均分 < 65 → red（高风险）
3. 最近一次未达标 或 存在未达标记录 或 历史均分 < 75 → yellow
4. 其余（最近一次达标 且 均分 ≥ 75）→ green（正常）

技术方案

接入真实大模型与语音的链路设计

架构说明

文字优先、语音按需，评分与 NPC 双角色分离

整条链路围绕「一次对话轮次」设计：学员在学员端发出内容（文字或语音），接入层把这一轮连同会话状态（第几轮、场景进度、已达成目标、历史对话）打包给 AI 能力层；ASR 先把语音转成文字，LLM 扮演客户 NPC 生成下一句回复与情绪，LLM 做 Rubric 评分在同一轮里对学员这句话打分并判定训练目标，TTS 把客户回复合成为语音条或通话语音回传；评分结果由编排层统一落库为 Record，供管理端看板、报告与风险分层消费。

两个 LLM 角色必须分离：NPC 追求「像客户」，要有情绪、会压价、会打断；评分器追求「像考核官」，要冷静、可解释、可复核。合成一个模型会互相污染，导致分数随客户演得投入而虚高。

降级策略：ASR/TTS 不可用时自动降级为纯文字；LLM 超时则回退到场景剧本 script[i] 的预设台词与关键词评分，保证练习不中断，并在记录上标记 channel 与降级标识。

图 4 · 目标架构：ASR → LLM（客户 NPC + Rubric 评分双角色）→ TTS，会话状态管理与评分落库由编排层统一负责

P9 已交付
列表分页统一口径 + 辅导记录检索 + 审计翻页
 未交付清单里的两项技术债：① 五个列表接口（`/records` `/learners` `/tasks` `/coach-notes` `/audit`）一次返回全量，数据量大时会拖垮调用方；② 审计日志的老实现是「先 LIMIT 再 JS 过滤」——带范围的账号看到的行数比 limit 还少且没有 total，分页语义是错的（3900+ 条审计只有最新 100 条能看）。现在统一补齐：分页五件套 `?limit=&offset=` → `{ items, total, limit, offset, hasMore }`，`total` 是筛选后总数；参数校验 `limit∈[1,500]`、`offset≥0`，非法一律 400（宁拒不猜，防 `limit=0`/负数/巨值拖库）；翻页配稳定排序（`at DESC, id` 次级键定序——同 `at` 的行不排序会在两次请求间漂移，翻页重/漏行）；不带分页参数仍是全量（三端「一次拉全量 + 本地统计」是刻意的离线兜底架构，audit 例外：无参默认最近 100 条，只增不减的表不能全量）。辅导记录检索：`/coach-notes?q=` 全文包含，LIKE 通配符 `%`/`_`/`\` 先转义（用户输入按字面匹配，`q=%` 不会变成「匹配任意」）。消费端：管理端服务端页的审计卡片升级为翻页浏览（每页 40 条、上一页/下一页、越界双保险），同步层 `auditLog({limit,offset})` 带回 `total`/`hasMore`。 1）分页语义：翻页两页无重叠且都在全量里、`total===全量`、首页 `hasMore=true`、`total` 不因分页/与 `learnerId`、`mode` 组合而变 ✅；2）非法参数 5 种（`limit=0`/`501`/`abc`/`2.5`、`offset=-1`）全部 400 ✅；3）向后兼容：无参仍回全量（28/28）、学员端匿名 `?learnerId=&limit=` 同口径、三端水合与现有 202 条断言零改动全绿 ✅；4）检索：关键字命中且只含命中行、不命中返回空、`q=%` 与 `q=_` 都按字面匹配返回 0 条（不转义会返回全表，实测命中 2 → 已拦住） ✅；5）审计：默认 ≤100 条且 `total/hasMore` 如实、翻页无重叠、范围（dept）账号的审计条数 === total（SQL 化修正了「先 LIMIT 再过滤」的老坑）、只含本部门与自己 ✅；6）五处注入飞证全部如期变红并还原：上限放宽（6 红）、`hasMore` 恒假（6 红）、LIKE 转义删除 + audit 默认截断删除（4 红）、管理端翻页拦截删除（1 红），还原后三套自测全绿 35 / 179 / 214，连跑幂等 ✅。 「接口分页」与「辅导记录检索」从未交付清单关闭（分页为服务端能力，三端 UI 保持全量水合是刻意架构）；生产上线仍需：HTTPS / 反代、进程守护、语音通道 ASR / TTS。分页 500 上限为编译期常量。

P0 留下什么

一套可演示、可体验的学员端，验证了「微信式陪练」这个形态在新员工中的接受度；同时定义了 5 维能力口径、3 个场景剧本与报告结构——这些在 P2 换模型后全部复用，只有打分实现被替换。

P1 的关键取舍

本轮不碰模型，把「管理动作 + 带教动作 + 内容动作」跑通：下发、追踪、分层、辅导、质检、场景自助编辑，并为内容补上落库 / 版本 / 审批三道治理闸门。先冻结数据口径与评分引擎两条命脉，P2 换模型时三端零改动。因此 P1 的验收重点不是功能多，而是口径一致。

P2 验证了什么

P2 的最大不确定性不是模型能不能打分，而是打的分和主管心里的分是不是一回事。因此交付重点放在金标集校准链路而非更聪明的模型：实测 Pearson 0.885 说明模型排序与人工判断高度一致，但 MAE 13.8 说明绝对分系统性偏高，Rubric 需要收紧——这条结论本身比「接入成功」更有价值。分维上「方案讲解 0.577」最弱，是最该补锚点的维度。

P3 补上了什么

P2 交付了服务能力，但还差「能不能真的给别人用」。P3 不新增功能，专补三处硬伤：①权限是自觉还是强制——删掉「收不到操作人即默认超管」的回落，加上登录与 token，越权从「靠约定」变成「服务端拦」；②多人协作是真的还是假的——场景改动从只写浏览器本地改为写服务端，运营 A 编的场景运营 B 能看到；③崩了怎么办——启动脚本、一键备份、恢复出厂、49 项端到端自测。仍差的（语音、任务落库、HTTPS、守护进程）都已列在 P3 行的前置依赖里，不含糊。

P4 为什么先做这两件

P3 把「服务能收数据」解决了，但业务闭环里还有两处是假的：任务下发只在管理端内存里转一圈、学员根本收不到；staff 接口谁都能读全量、教练看得见全公司成绩。这两条都不是「锦上添花」，而是一试用就会被戳穿的诚实性问题，所以 P4 不铺新功能，先把它们做真——下发真的到达学员、可见范围真的按角色收口。顺带把管理端从「读页面加载时的静态数据」改成「回拉服务端后原地水合」，这样三端数字继续同源，不会长出第二套统计口径。

P5 补上了什么

P1 就交付了教练工作台，但它是三端里唯一始终没接服务端的：身份写死在页面里、读静态数据源、辅导记录与质检结论只存在内存里，而 UI 文案却在说「交接给下一次带教」「转交培训运营更新剧本」——界面在说谎，比缺功能更严重，所以 P5 优先把它做真。两个设计判断值得记下：① 教练的写权限刻意不卡 can_edit，因为写辅导、做质检正是带教主管的本职，而教练角色的 can_edit 本来就是 0，卡它就等于把教练台变成只读页；该卡的是可见范围。删成绩才属于内容运营动作，才卡 can_edit。② 老库升级只建表不补内容是常见疏漏，P5 把它当成缺陷修掉——凡「升级后开箱仍可用」的承诺，都要有对应的迁移动作，不能只靠「重新播种」。

P6 为什么是它

P4 让任务「下发真的到达学员」，但场景这一半还是断的：学员端的场景库在页面加载时就定死了，运营新发布的场景学员根本看不到。也就是说「下发 → 学员练」这条闭环只对老场景成立，对每一个新场景都是断的——而它不报任何错，只在学员那头表现为「就是没有这个场景」，运营那头的界面还一切正常。这类「静默的断点」比崩溃危险得多，所以 P6 只做一件事：把它接上。
实现上最大的难点不是加接口，而是合并语义。三个约束都来自学员端已有的实现：①不能重排（cur 是数组下标、SCENES[cur] 在几十处实时求值，重排会让「当前会话」指向别的场景）；②不能删本地种子（服务端库可能不全，清掉就让学员没场景可练）；③不能换引用（HELPERS 闭包持有数组引用、?demo 分支会先抓 SCENES[0] 再回填）。这三件事全都不会有报错，只能靠断言看住——所以 P6 的验收重点不是「功能有了」，而是「这些约束有测试看着」。

P7 为什么是它

P2 起每轮对话就落进了 session_turns 表，但它从来没有读的路径：没有读的路由，两个页面里连 evidence 这个词都搜不到，演示库 28 条成绩的逐轮明细非空 0 条。于是教练台的「逐轮复盘」整块是拿场景剧本拼出来的——客户的词、一句「参考表达」，而学员当时答了什么一个字都没有；更糟的是那一屏、那个按钮都叫「对话质检」。一个看不到对话的对话质检，比没有这个功能更危险：主管以为自己是在按原话点评，实际是在对剧本发表意见，而且这些结论会被写进辅导记录、交接给下一次带教。
所以 P7 只做一件事：把这条读路径接通。
过程里最值得记下的不是接口本身，而是两处静默失真：①同一份数据有两种形状——finish() 返回的逐轮对象用 learnerText，落库的 evidence 用 learner，前端照前者写就会读到 undefined——不报错、不抛异常，只是空白（这是本项目第二次踩同一个坑，因此现在定成硬规矩：逐轮对象的形状只允许在 turnRow() 里定义一次，读旧数据必须显式归一化）。②口径必须精确到「分」——finish() 的维度分是「逐轮算术平均再取整」，给演示数据补逐轮分时若随手取整，教练台就会并排显示「逐轮均分 72 / 总分 58」，看的人只会以为系统坏了；所以补数据用 spreadExact() 把逐轮和配到与总分严丝合缝。这两处都不抛异常，只能靠断言看住——这也是 P7 把自测扩到 147 + 185 项、并把教练台渲染函数真源码搬进沙箱跑的原因。

单机部署的并发与落盘策略 中 服务端是「单进程 + 同步 SQLite」，写入天然串行；若落盘级别、模型配额或磁盘性能不匹配，会表现为「人一多就卡」——而且功能全对、不报任何错，最容易被误判成「网络慢」或「模型慢」。 把容量当成交付项而不是上线后再说：①落盘级别——SQLite 出厂默认 synchronous=FULL 在 WAL 下每次提交都 fsync，实测单条写入提交 43.96ms（NORMAL 仅 0.06ms，约 700 倍）；更坑的是 fsync 阻塞单线程事件循环，写入并发时读接口从 2ms 劣化到 1.5s。本方案默认 DB_SYNC=NORMAL（WAL 官方推荐值，进程崩溃不损坏库，只可能丢最后几个已提交事务），/status 回报真实生效值、自测有断言看住，需要「断电也不丢」可设回 FULL。②容量按模型算，不按机器算——单轮真实模型调用 0.5–3s，再叠加供应商 RPM / TPM 限流，100 人同时练峰值也只有约 50 次调用/秒，服务端远不是瓶颈。③上限在哪：SQLite 单文件 + 单进程，实测写吞吐约 470 req/s、读约 1100–2900 req/s（够数百人同时练），再往上要迁 PostgreSQL 并考虑多进程分片。责任人：研发 + 运维。
两端数据口径漂移 中低 学员端与管理端各自实现一套统计，出现「学员看到已达标、主管看到未达标」这类互相打脸的 bug。 强制唯一真相源：所有统计只允许调用 TRAIN.helpers，禁止各端自写聚合；口径变更只改数据源并被两端自动继承；看板数字必须在验收时与 helpers.overview() 逐项对齐。责任人：研发（代码评审卡点）。
对专家的判断 中低 附赠风险，需提醒业务方：评分标尺本身是否被业务认可，比技术实现更决定成败。 P1 期间由业务方参与制定 5 维 Rubric 锚点（高 / 低分特征），而不是研发单方面定义；先把「什么样的回复算好」写成双方签字的口径，再交给模型执行。
